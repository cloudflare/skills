# Workers Builds Configuration

## Commands

Workers Builds runs an optional build command and then a deploy command.

| Context | Typical command | Result |
|---------|-----------------|--------|
| Build | `npm run build` | Produces framework or static output |
| Production deploy | `npx wrangler deploy` | Deploys to production |
| Non-production deploy | `npx wrangler versions upload` | Uploads a preview version without changing production traffic |

Use the package scripts generated by a framework when its current Cloudflare
guide specifies different commands. Pin Wrangler in `devDependencies` so local
and managed builds use the same version.

Workers Builds does not currently honor Wrangler Custom Builds configuration.
Configure its build command in Workers Builds instead.

## Production and Preview Triggers

Treat production and preview as separate triggers. Verify the effective branch
rules, commands, variables, and token for the trigger that actually ran. Do not
assume a production setting also applies to preview builds.

The production branch deploys to the live Worker. Non-production builds use the
preview deploy command and can provide preview URLs and Git pull-request
feedback. Retrieve the current preview documentation before promising support
for a particular binding, custom domain, Durable Object, Container, or Workers
for Platforms setup.

## Root Directory and Monorepos

Set the root directory to the project containing the relevant `package.json`
and Wrangler configuration. The Worker name in that configuration must match
the connected Worker.

Use build watch paths to include project code and shared dependencies while
excluding unrelated paths. A root directory changes where commands run; it does
not necessarily prevent a package manager from installing the whole workspace.
Use package-manager filtering when dependency installation must be scoped.

## Build Variables and Runtime Variables

Build variables and secrets are available only while the build runs. They are
not runtime bindings or Worker secrets. Configure runtime values in Wrangler or
the Worker's **Variables & Secrets** settings.

Workers Builds injects CI metadata, including:

- `CI`
- `WORKERS_CI`
- `WORKERS_CI_BUILD_UUID`
- `WORKERS_CI_COMMIT_SHA`
- `WORKERS_CI_BRANCH`

Branch names can contain characters that are invalid in another destination,
such as a preview alias. Validate or normalize a value before reusing it as an
identifier.

## Build Tokens

A build token authorizes Workers Builds to deploy resources. It is different
from a token used to call the Builds REST API.

- Prefer one intentionally selected token with the required permissions.
- Verify which trigger references a token before rotating or deleting it.
- After rotation, confirm a new build uses the intended token.
- Do not repeatedly delete tokens as generic troubleshooting. A stale trigger
  association may require inspection or support rather than another token.
- Retrieve current documentation before stating whether user-owned or
  account-owned tokens are supported.

## Caching and Watch Paths

Build caching can preserve dependencies and framework outputs between builds.
Cache only reproducible content and use the current framework guidance to choose
directories. When debugging, compare cache-enabled and cache-disabled runs; do
not delete lockfiles or source configuration.

Watch paths control which repository changes trigger a build. In a monorepo,
include shared packages and lockfiles that can affect output, not only the
application directory.

## Limits and Pricing

Always retrieve the current limits and pricing page. Build minutes, resource
sizes, timeout, concurrency, variable limits, and included usage can change.
When enabling every non-production branch, call out the effect on build-minute
usage and recommend monitoring or path filters.
